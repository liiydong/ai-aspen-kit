# 脚本库索引

> **383 个脚本不是 383 个工具，而是一条时间线。**
> 每个脚本 = 一次「提出假设 → 改模型 → 跑一次 → 读结果 → 得出结论」的循环。
> `run_s9.py` 的意思就是「第 S9 步」。

这份索引帮你**按项目推进的顺序**读懂这个库，而不是面对一堆文件名发懵。

**三种读法，按你的目的选：**

## 一、主线：模型是怎么长出来的（61 个）

模型从 **14 模块 / 29 流股** 长到 **36 单元 / 61 流股 / 15 组分 / 0 警告**，全部由这 61 个脚本推进。**按编号顺序读，就是完整故事。**

### 第 1 阶段：扩展「反应与吸收段」（R1–R4）

| 脚本 | 做了什么 |
|---|---|
| `run_r1.py` | 加 C-101 空压机 / E-102 空气预热 / E-103 氨汽化 / E-105 废热锅炉 / T-202 尾气洗涤塔 |
| `run_r2.py` | 修正插入锚点 |
| `run_r3.py` | 修正 HEATER / COMPR 段落写法 |
| ~~`run_r4.py`~~ | R3 的重跑 —— **未收录**，原因见 [第六节](#六一个缺席的文件run_r4py) |

> **这一阶段暴露的规律**：往 `.bkp` 里插新模块，**必须三处同步** —— 文件头的块实例注册表、`FLOWSHEET` 段、块段落本身。少一处就报参数缺失。

### 第 3 阶段：产量攻关（S9–S13）★ 最精彩的一段

**目标**：把产量从 9850 t/a 提到 10000 t/a 以上。

| 脚本 | 改动 | 产量 | 结果 |
|---|---|---|---|
| `run_s9.py` | S-117（未反应 3-MP）直接回反应器 | 9850 t/a | ❌ **S-106 闪蒸不收敛，8 个 SEVERE ERROR** |
| `run_s10.py` | 加 **M-504 甲苯回收器**，把甲苯送回萃取塔 | 9574 t/a ↓ | ❌ 3-MP 被 T-402 挤到塔釜，从 S-119 跑掉了 |
| `run_s11.py` | T-402 采出比 0.040→**0.070**；M-504 改「按 S-117M 定分数」 | 9680 t/a ↑ | ✅ 0 错误 |
| `run_s12.py` | T-404 采出比 0.95→**0.99**，收回塔釜损失的 3-CP | 10089 t/a ↑ | ✅ |
| `run_s13.py` | M-503 母液排放比 0.12→**0.08** | **10221 t/a** | ✅ **定稿** |
| `run_s9_final.py` | 列出全部设备与连接、关键流股表，另存 `.apwz` | — | 交付 |

**这一段为什么值得读：**

- **S9 的失败是最有价值的**：甲苯进了 405 ℃ 反应器，**NRTL 处理不了** → 闪蒸不收敛。
  **结论：必须在低温段先把甲苯分离掉。** 这一条改变了整个回收路线的设计。
- **S10 的倒退也是**：加了设备反而产量掉了。原因是「回收」和「采出比」是一对耦合变量，只动一个会按下葫芦浮起瓢。
- **最终成绩**：10221 t/a（超设计 2.2%）、单耗 910.7 kg/t（设计 936.89）、总收率 83.73%

### 第 5 阶段：纯度与收率修复（P1–P11）

**目标**：产品纯度掉下来了，把 3-CP 收率找回来。

| `run_p6.py` | 甲苯回路展开为一次通过（S-111 = 2254.9 kg/h） |

### 第 6 阶段：T-403 的 4-CP 难题（Q1–Q3）

**背景**：4-CP（4-氰基吡啶）来自原料 4-MP 的氨氧化，**是全流程最难分离的一段**（相对挥发度 α≈1.05）。

| 脚本 | 做了什么 | 结论 |
|---|---|---|
| `run_q1.py` | 核对组分身份 + 让 T-403 真正把 4-CP 赶到塔顶 | 库中**缺 3-CP/4-CP 二元 VLE 数据**，严格塔算不动 |
| `run_q2.py` | T-403 改 **Sep**（4-CP 从塔顶采出作副产，按工业实测方向） | 等效建模 |
| `run_q3.py` | T-403 改 Sep（**只改 T-403 自己的 `FLOWSHEET` 条目**，不误伤 T-404） | ✅ |

> **这是全项目「诚实建模」的典范**：算不了就如实说明，而不是硬凑一个数。
> 论文 §4.3.3 专门写了这一段（与 T-301 萃取塔同一处理逻辑）。

### 第 7 阶段：二元交互参数攻关（bip / est / inj）

**背景**：`NRTL-1` 参数表是空的，但模型照样能跑。用户质疑「数据从哪来」。

| 脚本 | 做了什么 |
|---|---|
| `run_bip1.py` | 补 `DATABANKS` 声明，看 Aspen 是否自动检索 NRTL 二元参数 |
| `run_bip2.py` | 测试预测型物性方法 `UNIF-LL` / `UNIFAC` 能否让萃取塔分相 |
| `run_bip3.py` | 给 NRTL 参数段补 `BDBANK` 检索清单 |
| `run_bip4.py` | 正确插入 `BDBANK`；并注入水-甲苯 NRTL 实测参数验证机制 |
| `run_bip5.py` | 运行 BDBANK 版并回存，解析 Aspen 实际检索到的参数 |
| `run_est1.py` / `run_est_all.py` | 设 `ALLONLY` 打开全局估算 + `ESTIMATE=YES`，看参数是否生成 |
| `run_inj.py` / `run_inj2.py` | 跑通注入了真实二元参数的模型，采集关键结果 + **用正确的 COM 等待方式**并抓控制面板 |

**三个关键结论：**

1. **判断"参数有没有生效"看什么**：不是 COM 的 `NRTL-1\Output\CID1`（那个**永远是 0 行**，连出厂示例 `glycols.bkp` 也是），
   而是**保存文件后数文本里的 `UVAL` 条数**。
2. **`Run2()` 不执行「从数据库检索二元参数」** —— 那一步只在 GUI 访问参数页时触发，COM 无法调用。
3. **最终解法**：扫描 **518 个 Aspen 自带 `.bkp`**，筛出本体系组分的**真实参数 5 对**直接写入模型。

**决定性对照实验：**

| 指标 | 理想溶液 | 含 5 对真实参数 | 偏差 |
|---|---|---|---|
| 产品 S-209 | 1419.529 | 1419.256 | **−0.019%** |
| T-401 冷凝负荷 | −0.9258 | −0.9257 | **−0.007%** |
| Terminal/Severe/Errors | 0/0/0 | 0/0/0 | — |

→ **全流程变化 < 0.02%，此前所有结论（产量、纯度、单耗、收率）验证稳健。**

## 四、一条完整的例子：产量从 9850 爬到 10221

**把 `run_s9` → `run_s13` 连起来读，就是一段完整的工程攻关叙事：**

```
┌─ run_s9.py ────────────────────────────────────────────┐
│ 想法：S-117 里的未反应 3-MP 直接回反应器，不就回收了？   │
│ 结果：产量 9850 t/a，但 S-106 闪蒸不收敛（8 个 SEVERE）  │
│ 学到：✗ 甲苯进 405℃ 反应器 → NRTL 处理不了              │
│       → 必须先在低温段把甲苯分离掉                      │
└────────────────────────────────────────────────────────┘
                        ↓
┌─ run_s10.py ───────────────────────────────────────────┐
│ 想法：加 M-504 甲苯回收器，把甲苯送回萃取塔             │
│ 结果：产量掉到 9574 t/a（倒退！）                        │
│ 学到：✗ 3-MP 被 T-402 的 D:F=0.040 挤到塔釜，从 S-119 跑了│
│       → 「回收」和「采出比」是耦合的，只动一个不行       │
└────────────────────────────────────────────────────────┘
                        ↓
┌─ run_s11.py ───────────────────────────────────────────┐
│ 改动：T-402 采出比 0.040 → 0.070                        │
│       M-504 改为「按 S-117M 定分数」（甲苯一点不进反应器）│
│ 结果：9680 t/a，0 错误 ✅                                │
└────────────────────────────────────────────────────────┘
                        ↓
┌─ run_s12.py ───────────────────────────────────────────┐
│ 改动：T-404 采出比 0.95 → 0.99                          │
│ 理由：收回塔釜损失的 63.7 kg/h 纯 3-CP                   │
│ 结果：10089 t/a，单耗 922.5 kg/t ✅                      │
└────────────────────────────────────────────────────────┘
                        ↓
┌─ run_s13.py ───────────────────────────────────────────┐
│ 改动：M-503 母液排放比 0.12 → 0.08（精制收率锁 97%）     │
│ 结果：10221 t/a、99.62%、单耗 910.7 kg/t、收率 83.73%   │
│       0 错误、物料平衡偏差 0.0000% ✅ 【定稿】           │
└────────────────────────────────────────────────────────┘
```

**这段叙事里有三个通用教训：**

1. **失败比成功信息量大**。S9 的 8 个 SEVERE ERROR 直接否定了整条回收路线，逼出了 M-504 的设计。
2. **不要一次改两处**。S10 同时加设备 + 沿用旧采出比，倒退后无法判断是谁的锅。
3. **上下游是耦合的**。塔的采出比、母液排放比、循环量互相咬住，要「反解 + 两点标定」而不是拍脑袋。

## 五、使用提醒

1. **环境不同**：脚本里有大量硬编码绝对路径（已替换为占位符，见 [`../来源与许可.md`](../来源与许可.md)），移植时需先替换。
2. **多为一次性工具**：写的时候以「这一轮排查够用」为目标，缺少参数化与错误处理。
   要长期复用，建议按功能归类、补 docstring、抽出公共模块。
3. **COM 脚本耗时**：凡 `win32com` 打开模型的脚本，单次运行 3–10 分钟，请后台执行。
4. **两个 Python 环境**：
   - COM 脚本 → 装了 `pywin32` 的那个（本机为 `D:\<化工运行时>\python-env`）
   - 表格/文档处理 → 装了 `openpyxl` / `python-docx` 的那个
5. **有些脚本是「同一次改动的多次尝试」**：`fix_all_v2`~`v6`、`run_v10`~`v12`、`run_p1`~`p6` 都属于这类。
   读的时候看**最后一个成功的**，前面的看思路即可。

## 六、一个缺席的文件：`run_r4.py`

本目录**有 383 个脚本，而不是 384 个** —— `run_r4.py` 没有收录。说明如下：

**原因**：该文件的中文注释在原始存档中已被 **GBK 双重编码损坏**，而且损坏是**散布式**的 ——
除了中文变乱码，还有**闭合引号、空格、甚至换行符被吃掉**，导致整个 `.py` 文件无法被 Python 解析。

**为什么不用猜的方式补回来**：缺失的字符已经**不可逆丢失**。按语义硬猜着填，
等于**伪造**一份并非作者原稿的文件 —— 那比缺一个文件更糟。

**它的内容在哪**：经逐行比对确认，`run_r4.py` 的**代码与完好的 [`run_r3.py`](./run_r3.py) 完全相同**，
仅输出文件名不同（`..._r3.bkp` → `..._r4.bkp`）。它属于 **R3 步骤的重跑**，没有任何独有内容。

> **想看那一步做了什么，直接读 [`run_r3.py`](./run_r3.py) 即可。**

**这条本身也是一个教训**（与第三节的「bkp 文本格式」呼应）：

> 改文件时如果不控制编码，损坏往往不是"全坏"或"全好"，而是**散布式的局部丢失** ——
> 表面看还能读，实际已经缺了几个字节。**这类损坏最难发现，也最难修复。**

本仓库的构建流程因此加了【真语法自检】（用 Python 的 `ast` 逐个解析全部脚本），
就是为了让这类问题**不会被静默发布出去**。
